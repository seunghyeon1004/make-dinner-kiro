This is the front end up to the moment cooking starts: the app shell and three of the four screens (Menu, Steps, Plan). Cooking mode is a separate spec (`cooking-mode`); design the shared state so that spec can add its screen without reshaping yours. Read docs/BRIEF.md ("The product, end to end", "Design direction"), the steering (ui.md is the design contract: tokens, type, targets, accessibility, copy; structure.md fixes src/web layout; product.md the flow and glossary), and the specs recipe-graph, scheduler, dinnerfile and recipe-reader (use their exact types and API shapes; if one of them is missing something the UI needs, list it under "Needs from other specs" rather than inventing it). Follow the format of the earlier specs (EARS requirements with ids, design with real paths and exact signatures, test-first tasks.md with ids, files, requirement ids and proving commands; "(decided here)" marks; decisions and open questions at the end of your reply).

What the person can do, each a requirement group:
1. Open the URL and see a schedule fast: the Menu screen lists the sample dinners from GET /api/samples (title, blurb, dishes); choosing one loads its recorded plan and goes straight to the Plan screen with the sample's suggested kitchen and a serving time (decide the default: e.g. the next half hour that leaves enough time). No login, no model, works with the key unset.
2. Paste their own recipes: a large text area, a character counter against the 12,000 limit, "Read recipes" calls POST /api/parse, a busy state that says what is happening (a model call takes several seconds), and every error code from the recipe-reader spec turned into a plain sentence with what to do next (rate limited: when to retry; cap reached or no key: use a sample or paste a Dinnerfile). Success goes to the Steps screen.
3. Paste or upload a Dinnerfile instead: parsed in the browser by core, line-numbered errors shown under the text area.
4. Review and correct steps (Steps screen): dishes as sections, steps in dependency order; edit title, minutes, appliance, hands-on, hold (a "keeps" toggle plus minutes) and prerequisites (a checklist of the other steps, same dish first); add and remove steps and dishes; rename dishes. Sanity issues from validatePlan appear beside the step or dish they concern and in a summary at the top; errors block "Make the plan", warnings do not. Removing a step that others depend on asks what to do (decide: remove it from their prerequisites and say so).
5. Plan screen: kitchen steppers (burners, ovens, cooks) and the serving time; the schedule recomputes on every change in the browser via core. Show: when to start, total span, the timeline, the plan list, warnings (hold_exceeded with the dish named), and a note when the start time is already in the past ("This dinner needs 1 h 50 min. Earliest serving time 19:25" with a button that sets it). A missing appliance (the plan needs an oven, the kitchen has 0) is explained and blocks only the schedule.
6. The timeline: one row per lane (Cook 1.., Burner 1.., Oven 1..) plus rows for hands-free steps that use no appliance (resting, rising: pack them into as few rows as needed, labelled "Hands-free"), a time axis in clock time, a "serve" line, bars labelled with the step title where it fits, bar styles per ui.md (hatched oven, solid burner, dashed hands-free), critical steps marked. For steps whose result keeps and that sit back to back with slack 0, do not call them Critical: the word is reserved for slack 0 on a step whose result does not keep (decided in review); say "Back to back" for the others. Tapping a bar focuses that step in the plan list. The graphic is aria-hidden; the plan list carries everything (ui.md). Horizontal scroll inside the timeline only, never the page.
7. The plan list: ordered by start, grouped under clock-time headings, each item with time range, title, dish, lane(s), minutes, slack or the critical mark, wait warnings. This is the text alternative and the print layout.
8. Export and share: "Dinnerfile" opens a panel with the text in monospace, Copy and Download (file name Dinnerfile), and one line explaining `make -n -f Dinnerfile dinner`; "Share link" copies a URL whose fragment holds the plan, kitchen and serving time (design the encoding: versioned, compact, URL-safe, validated on load through validatePlan; state the size for the largest sample and what happens beyond a sensible URL length); "Print" uses print.css: plan list and Dinnerfile only, black on white.
9. Shell: header with the product name and a theme switch (system, light, dark), the four steps of the flow as navigation that shows where you are and what is not reachable yet, state kept in localStorage so a reload returns to the same place with the same plan, "Start over" with a confirmation. Routing by URL fragment. Offline after first load is a goal for the scheduling paths: no request is needed after the samples have loaded.
10. Error and empty states for every screen, written out as copy in the design.

Design must fix: the store shape and its pure reducer-style functions (testable without a DOM), which component owns what, the time mapping between scheduler minutes and clock time (one module, tested, including serving after midnight and locale formatting through Intl), the share-link codec with a round-trip property, how the timeline maps minutes to pixels and labels, the exact copy for buttons, headings, errors and empty states (ui.md copy rules), and the test plan: unit tests for store, time, share codec, timeline layout (pure functions); Playwright e2e for the flows (sample to plan in two taps; paste with a faked /api/parse route for success and for each error; Dinnerfile import; edit a step and see the schedule change; kitchen change; share link round trip in a new page; print media snapshot of structure, not pixels) on the phone and desktop projects, each screen with an axe check, light and dark.

Tasks: order them so the app is usable early (shell, store, Menu with samples, Plan with list, then timeline, then Steps editor, then paste and import, then export/share/print, then polish and the full e2e pass). About 30 to 40 sub-tasks, each small enough for one sitting, each with its proving command.

Also read the rebuild spec's "The axis and servingMin" section: after a rebuild the serving minute is not 0, so the time-mapping module must take the schedule's serving minute into account from the start.
