A self-dependency stays in `prereqs` as a self-loop. Every\nalgorithm is iterative (N2).\n\n- **successors**: for each node `s` and each `p` in `prereqs(s)`, add `s` to `succ(p)`.\n  Map keys are inserted in id order; values sorted. A self-loop makes a node its own\n  successor.\n- **terminalSteps**: nodes whose `succ` is empty, in id order.\n- **topologicalOrder**: Kahn's algorithm. `indegree(s) = |prereqs(s)|`. Keep the ready\n  nodes in an array sorted by id; repeatedly remove the smallest, append it, and decrement\n  its successors. If fewer than all nodes are placed, return the cycle error: the\n  smallest-id self-loop node `x` gives path `[x]`, compared against `findCycles()[0]` by\n  first id; the smaller first id wins.\n- **findCycles**: `reach(x)` = nodes reachable from `x` along `p → s` edges (BFS, self-loops\n  ignored). Nodes `x != y` are in one group iff `y ∈ reach(x)` and `x ∈ reach(y)`. For each\n  group of size >= 2 with smallest id `m`: BFS from `m` inside the group, visiting\n  successors in id order and recording the first parent, until a node `v` with\n  `m ∈ succ(v)` is dequeued; the path is `m … v`, rebuilt from parents. This is the\n  shortest cycle through `m`, ties broken by id. Paths are returned ordered by first id.\n  `path[i] ∈ prereqs(path[i+1])` and `path[last] ∈ prereqs(path[0])`. Cost\n  O(n · (n + e)), fine at 80 steps.\n- **longestChainMinutes**: if `topologicalOrder` fails, return its error. Otherwise in that\n  order `chain(s) = minutes(s) + max(0, chain(p) for p in prereqs(s))`; return the maximum.\n\n## `src/core/sanity.ts`\n\n```ts\nexport function parsePlan(input: unknown): Result<Plan, Issue[]>;\nexport function parseKitchen(input: unknown): Result<Kitchen, Issue[]>;\nexport function checkPlan(plan: Plan): Issue[];\nexport function checkKitchen(plan: Plan, kitchen: Kitchen): Issue[];\nexport type PlanCheck = { plan: Plan; issues: Issue[] } | { plan: null; issues: Issue[] };\nexport function validatePlan(input: unknown): PlanCheck;\nexport function sortIssues(issues: readonly Issue[]): Issue[];\nexport function hasErrors(issues: readonly Issue[]): boolean;\n```\n\n### `parsePlan`\n\n1. `PlanSchema.safeParse(input)`. ## Decisions marked "(decided here)"

**Schema and limits**
1. `holdMin` is `null` or a whole number from 0 to 480.
2. A dish id has at most 40 characters and a step id at most 80. An `after` list has at most 80 entries.
3. Text limits are counted in UTF-16 units, and the text must contain at least one non-space character:
   - plan title: 1 to 120
   - dish name: 1 to 80
   - step title: 1 to 120
   - step detail, when present: 1 to 1000
4. Objects are strict: an unknown key is an `invalid_field` error.
5. The parse codes are `invalid_field`, `minutes_out_of_range`, `empty_plan`, `too_many_dishes` and `too_many_steps`. Issues may carry `dishId` and extra fields for their code.
6. A message for an element with an invalid id names it by position (`Step 4`), and `field` keeps the 0-based path (`steps[3]`). Messages never include titles, names or details.
7. Issues are sorted errors first, then by code, step id, dish id and the code's extra fields, with exact duplicates removed.

**Graph**

8. Ids are compared by UTF-16 code units, never by locale.
9. A step id that occurs twice is one node: its `after` lists are merged and its largest `minutes` is used. `after` entries that name no step are ignored.
10. A cycle is reported once per group of steps that wait on each other. The path starts at the group's smallest id and follows the shortest cycle through it. A self-dependency is reported separately, not as a cycle.
11. No recursion anywhere, so the functions work on plans of any size.

**Rules**

12. The words that trigger `appliance_mismatch` include inflected forms ("roasting", "stir-fry", "saute" without the accent). "ovenproof", "boiler" and "roaster" do not trigger it.
13. `validatePlan` is the one pipeline (parse, then check) that the parse route, Dinnerfile import, share link and MCP server all call.
14. `parseKitchen` is added alongside `parsePlan`.
15. The rule that a step id starts with its dish id is a prompt convention, not a sanity rule.

**Canonical form and normalisation**

16. `canonicalPlan` and `compareIds` live in `schema.ts`, so no new file is added to `structure.md`'s layout.
17. `after` is treated as a set: canonical form sorts it and removes repeats.
18. A lone CR is turned into LF, as CRLF is.

**Tests**

19. Extra generators: `arbShuffledPlan`, `arbPlanLikeValue`, `arbRecipeText`. `arbBrokenPlan` returns `{ rule, input, kitchen, target }`.
20. The new property ids are P-RG1 to P-RG9, and the file each one lives in is fixed in the design.
21. `fcParams()` sits in `test/support/fc-params.ts`. Tests about the test support go in `test/meta/`.
