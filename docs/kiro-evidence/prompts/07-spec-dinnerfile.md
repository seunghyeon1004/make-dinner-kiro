Write the spec `dinnerfile` in .kiro/specs/dinnerfile/: requirements.md, then design.md, then tasks.md. No code in this session.

The Dinnerfile is the visible seam of this project: a plan exported as a real Makefile that GNU Make accepts and that the app reads back without the model. Read docs/BRIEF.md ("The chimera"), .kiro/steering/product.md ("The Dinnerfile"), scheduler-guarantees.md (D1, D2) and the recipe-graph spec (types, canonicalPlan, validatePlan, generators). Follow the format of the recipe-graph spec exactly (EARS requirements with ids, design with real paths and exact signatures, correctness properties with ids and generators, test-first tasks.md with ids, files, requirement ids and proving commands; "(decided here)" marks; decisions and open questions at the end of your reply).

Scope:
- `toDinnerfile(plan, options?)` and `fromDinnerfile(text)` in src/core/dinnerfile.ts, pure. Export writes canonical order. Import returns Result<Plan, DinnerfileError[]> with 1-based line numbers and messages a person can act on, then the caller runs validatePlan as for any other source.
- The exact grammar, written down as a grammar: header comments, `# plan`, `# dish`, `# step` metadata lines, one target per step with its prerequisites, the `@echo` recipe line (tab-indented, as Make requires), an aggregate target per dish (so `make -n -f Dinnerfile <dish-id>` works for one dish), the `dinner` target, `.PHONY`. Decide and state how the kitchen and serving time may be recorded as optional comments (`# kitchen burners=4 ovens=1 cooks=1`, `# serve 19:00`) that import returns alongside the plan and that never affect Make.
- Escaping, which is where this goes wrong: titles and details are free text and may contain `'`, `"`, `$`, `#`, `\`, backticks, `:`, `=`, `%`, tabs, newlines, leading/trailing spaces and non-ASCII. State the encoding for the comment metadata and for the `@echo` argument so that (a) D1 holds for every valid plan, (b) `make -n` prints each title, (c) nothing in a title can make Make or the shell run anything. The echo line is for humans; import must read data only from the comment lines, never by parsing shell quoting. Show the worst-case example in the design.
- A dish id that equals a step id cannot happen (step ids contain a dot, dish ids do not); say what else could collide (`dinner`, `.PHONY`, a dish called `dinner`) and how it is handled.
- Tolerant import: CRLF, trailing whitespace, blank lines, unknown comment lines and reordered rules are accepted; hand-written files that omit `.PHONY`, the echo line or the aggregate targets are accepted; anything that would silently change meaning is an error (a target without a `# step` line, a `# step` line without a target, duplicate targets, prerequisites that disagree with nothing to say which wins, unknown keys in metadata, bad numbers).
- Properties: D1 (round trip on arbPlan, canonical), D2 (run the real `make -n -f <file> dinner` on the fixtures and on generated plans with a small run count stated in the design, since each run spawns a process; parse the printed echo lines and check every step appears exactly once in an order satisfying precedence; the test fails, not skips, if `make` is missing), plus P-DF properties you need: import never throws on arbitrary text; export output never contains a line Make would treat as anything other than a comment, a rule, a recipe line or blank; import(export(p)) ignores `options` comments correctly.
- An example test with one complete hand-written Dinnerfile for the small sunday-roast fixture, checked character for character against `toDinnerfile`.

Keep the tasks few and meaningful (aim for 12 to 18 sub-tasks): this is one file of code.
