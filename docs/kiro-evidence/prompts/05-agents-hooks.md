Set up this repository's Kiro automation: two custom agents and the workspace hooks. No application code, no spec changes. Use the formats this Kiro CLI version (3.2.0) actually loads; check with `kiro-cli agent validate --path <file>` (or the validate subcommand's real syntax, see `kiro-cli agent validate --help`) and `kiro-cli agent list`, and show me the output.

1. .kiro/agents/sous-chef.json: the builder. It implements exactly one spec task per session, test first, following the steering. It may read, write and run shell commands in this repo. Resources: every steering file and the specs directory. Its prompt is short and says what kiro-conduct.md says in five lines, plus: after each write a hook prints check results, read them and fix before moving on. Its hooks (these are the "run the scheduler's property tests on save" automation, in the form that fires in CLI sessions):
   - after every file write (postToolUse on the write tool): run `npm run typecheck`, and, if any file under src/core/ or test/core/ or test/support/ changed since the last run, also `npm run test:props` with FC_NUM_RUNS=50 for speed; print the last lines of each and the exit codes back to the agent. Keep it under 60 seconds; use a small script scripts/hooks/after-write.sh so the logic is readable and testable, and make the script append one line per firing (UTC time, what ran, exit codes) to docs/kiro-evidence/hook-fires.log.
   - when the agent stops: run `npm test` and `npm run test:props` (full run count) and `npm run lint`, print the summary lines, and append them to the same log (scripts/hooks/on-stop.sh).
   - on spawn: print `git status --short` and the unticked tasks (`grep -n "\- \[ \]" .kiro/specs/*/tasks.md | head -20`), and log the firing.

2. .kiro/agents/expediter.json: the checker (in a kitchen, the expediter inspects every plate before it leaves). It never edits src/, test/, e2e/ or steering. Its job: given a spec name, read requirements.md, design.md and tasks.md, then for every ticked task run the proving command the task names and read the code and tests it names, and report, per task: verified, or not verified with the reason (command failed, test does not exercise the thing, test mocks the unit under test, assertion compares a value with itself, file missing, requirement not actually covered). It may untick a task it cannot verify and add a one-line note under it; it may never tick one. It also looks for weakened checks: skipped tests, lowered run counts, narrowed generators, loosened schemas, eslint-disable or ts-expect-error. It ends with a table and the exact commands and counts it ran. Tools: read, shell, and write restricted (by its prompt and, if the agent format supports path restrictions, by configuration) to .kiro/specs/**/tasks.md.

3. .kiro/hooks/: workspace hooks in the format Kiro loads from this folder. Create:
   - a file-save hook on src/core/**/*.ts, test/core/**, test/support/** that runs the property tests (scripts/hooks/after-write.sh does the work, so the IDE hook and the agent hook share one script);
   - a file-save hook on src/web/styles/tokens.css that runs `npm run check:contrast`;
   - a file-save hook on .kiro/specs/**/tasks.md that runs a new script scripts/hooks/tasks-lint.sh, which fails if any tasks.md has a ticked parent with an unticked child, or a task line without an id; print the offending lines.
   Say honestly, for each hook, whether you saw it fire in this session and how; if a trigger cannot fire in a non-interactive CLI session, say so rather than claiming it works.

4. Prove the scripts work by running each once by hand and showing the output, including the tasks-lint script on a temporary bad tasks.md that you then delete.

Constraints: do not commit; do not edit steering, specs or docs/kiro-evidence (the hook scripts appending to hook-fires.log is the one exception); do not start watchers. scripts/hooks/*.sh must pass `bash -n` and be executable. Keep everything prettier- and eslint-clean (`npx prettier --check .`, `npm run lint`).
