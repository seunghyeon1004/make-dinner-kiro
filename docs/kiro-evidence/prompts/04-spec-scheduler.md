Write the spec `scheduler` in .kiro/specs/scheduler/: requirements.md, then design.md, then tasks.md. No code in this session.

This is the heart of the product: `schedule(plan, kitchen)` in src/core. Read docs/BRIEF.md (section "The scheduler"), .kiro/steering/scheduler-guarantees.md (G1 to G8 and the reviewed algorithm note: prep-forward moves every step whose result keeps, terminal or not; right-justify moves only steps whose result does not keep) and the recipe-graph spec in .kiro/specs/recipe-graph/ (this spec builds on its types, graph helpers, canonical form, generators and fixtures; do not redefine them).

Scope of this spec:
- The four passes (backward, prep-forward, right-justify, lanes) and the readout (slack, critical, waits, hold_exceeded warnings), in src/core/passes/ and src/core/schedule.ts, with a shared resource-usage helper in src/core/timeline.ts.
- The exact Schedule type: per step startMin, endMin, lanes, slackMin, critical, waitMin; plus spanMin, chainMin (the longest dependency chain, a lower bound shown to the cook), warnings, and the kitchen it was computed for. Arrays sorted by step id (G7.2).
- Errors as a typed Result: the plan fails the sanity error rules, or the kitchen lacks an appliance a step needs. The scheduler re-checks; it never trusts its caller.
- Deterministic tie-breaking stated precisely in the design, so two implementations of the design would give the same schedule.
- test/support/oracles.ts: the independent brute-force checkers the properties use (capacity per minute, precedence, completeness, waits, lanes, slack by trial), written without importing any scheduling code from src/.
- One property per guarantee id G1 to G8 (sub-ids G4.1, G4.2, G4.3, G5.1, G5.2, G5.3, G7.1, G7.2 each get their own property), and test/meta/guarantees.test.ts, which reads scheduler-guarantees.md and fails if any G id has no property whose title starts with it (it must tolerate R, S and D ids being covered by other specs: make it check the ids each spec has claimed so far, in a way the later specs extend rather than weaken; say how).
- Hand-worked example tests on the fixtures: for the small sunday-roast fixture, work the expected schedule out by hand in the design (a table of step, start, end, lane) for a kitchen of 4 burners, 1 oven, 1 cook, and for a second kitchen where a resource is scarce (1 burner) so that the passes visibly do something. The implementation must reproduce those tables exactly.
- A complexity note: the plan sizes are small (80 steps), so prefer the obviously correct loop over the clever one; state the worst case.

Think hard about the corner cases before writing requirements, and write a requirement or a design note for each: zero-capacity resources that no step needs; a single step; all steps hands-free; more cooks than steps; steps of 480 minutes; a prerequisite in another dish; a step with several successors (which one defines its deadline, which its wait); a keeps-step whose prerequisite does not keep; a keeps-step that is terminal; why the right-justify pass cannot break precedence or capacity; why the passes terminate; why the result does not depend on input order.
