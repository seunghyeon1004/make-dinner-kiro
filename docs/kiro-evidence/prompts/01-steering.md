This repository is empty except for docs/BRIEF.md (read it fully first), LICENSE, .gitignore and scripts/kiro-run.sh. Your job in this session is to write the steering files that every later Kiro session in this project will load. Write no application code and no specs.

Create these files in .kiro/steering/, each with the right front matter (`inclusion: always`, or `inclusion: fileMatch` with a `fileMatchPattern`), each short enough to be read in full every time (aim for 60 to 120 lines), concrete, and free of filler:

1. product.md (always): what Make Dinner is, who it is for, the three stitched technologies and what each is and is not allowed to do, the end-to-end flow, and what is out of scope. Include a short glossary (step, dish, terminal step, hold, slack, critical, lane, rebuild, Dinnerfile) so the same words are used everywhere.

2. tech.md (always): stack and versions policy (pin exact versions in package.json), commands (`npm test`, `npm run test:props`, `npm run test:e2e`, `npm run typecheck`, `npm run lint`, `npm run format`, `npm run build`, `npm run dev`, `npm start`), TypeScript rules (strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, ES modules with .js import suffixes on the server side), error-handling conventions (core returns typed results, never throws on bad input; the server maps them to JSON `{ error: { code, message } }`), environment variables, and the rule that the Anthropic key is never logged, returned, or bundled.

3. structure.md (always): the directory layout you propose for the brief's architecture (src/core pure and isomorphic; src/server; src/web for the Preact front end bundled into public/assets; src/mcp; samples/; recordings/; test/ mirroring src with `*.test.ts` for examples and `*.pbt.ts` for properties; e2e/; docs/kiro-evidence/), naming conventions, and the import rules (core imports nothing but zod; web and server import core, never each other).

4. scheduler-guarantees.md (always): the guarantees G1 to G8 and R1 to R6 from the brief, restated precisely enough to be turned into fast-check properties, with stable ids. State plainly that these are the product's promise: an implementation change may never weaken, delete, skip or narrow a property test to make it pass; a failing property means the scheduler is wrong (or the guarantee is, in which case stop and report). Also state that scheduling, rebuild, export and cooking mode never call a model.

5. testing.md (always): how tests are written here. Test first. A test must be able to fail: never mock the unit under test, never assert on a value the test itself constructed. Properties use fast-check with generators for valid plans and kitchens living in test/support/; each property names the guarantee id it proves. Recorded model output lives in recordings/ and is never hand-edited. No `.skip`, `.only`, `.todo` left behind. Report only test runs you actually executed, with the real counts.

6. ui.md (fileMatch: src/web/**, public/**, e2e/**): the design direction from the brief turned into rules: the kitchen-meets-terminal identity, design tokens to define (propose names and values for a light and a dark theme, warm paper and cast-iron tones, one accent), the two typefaces (use system font stacks, no web font downloads), counter-distance legibility (base size, minimum target 48px), one-handed reach, accessibility rules (the timeline has a text alternative that carries the same information; nothing by colour alone; visible focus; reduced motion; WCAG AA contrast, checked by a script), and copy rules (plain, short, imperative; no exclamation marks; no jokes in instructions).

7. kiro-conduct.md (always): rules for any agent working in this repo. Read the spec's three files before touching code. Implement only the task named. Never tick a task in tasks.md unless you ran the check that proves it in this session and it passed; when a task is partly done, leave it unticked and say what is missing. Never weaken a zod schema, a sanity rule or a property to make something pass. Never commit, push, or edit files under docs/kiro-evidence/ or .kiro/steering/ unless asked. Never print or log secrets. If the spec and the code disagree, stop and report rather than guessing.

Decide details the brief leaves open, but do not contradict it; where you make a decision the brief did not, mark it with "(decided here)". When done, print a list of the files written with a one-line summary each, and a list of every "(decided here)" decision so I can review them.
